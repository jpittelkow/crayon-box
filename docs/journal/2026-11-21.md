## Session: research, what a Linux version would take

**Asked:** what it would take to get the app on Linux. Research only; nothing built, no decision.

**Found**
- The web app and the family server already run on Linux (CI tests on Ubuntu; the server is a container).
- The shell is close: `kiosk.rs` already compiles its keyboard hook only on Windows, and the fs, opener, autostart
  and updater plugins all support Linux. Missing: a Linux bundle target (`bundle.targets` is `nsis` only), a Linux
  build job, a `linux-x86_64` entry in `latest.json` (`releaseManifest.ts` types only Windows), and a relaunch
  after an update (the NSIS installer restarts the app; an AppImage update does not).
- The real risk is the engine: Tauri on Linux draws with WebKitGTK, not Chromium. Untested there: the driving
  game's WebGL speed, the microphone recordings (WebKitGTK denies `getUserMedia` unless the shell answers the
  permission request), mp3 playback (needs GStreamer, bundled into an AppImage with `bundleMediaFramework`),
  touch and pen events, the speech fallback.
- The keyboard lock has no Linux twin on Wayland. The usual answer is a kids' account whose session is only the
  app (a kiosk compositor such as `cage`), which locks more than the Windows hook does.

**Next**
- If the owner wants it: say which Linux device, then a spike (the browser tests on Playwright's WebKit in CI, and
  a Linux build tried on that device) before an ADR.

## Session: the Linux trial build (in WSL, nothing changed in the repo's code)

**Done** (owner said the target is a touch laptop or PC, then "run the trial")
- Built the working tree for Linux in the dev machine's Ubuntu 26.04 WSL distro: Ubuntu's own Node 22, Rust 1.93.1
  and WebKitGTK 2.52.6. The program (16.6 MB), a `.deb` (12.9 MB, depends on `libwebkit2gtk-4.1-0` and
  `libgtk-3-0`) and an AppImage (96 MB, it carries WebKitGTK) all built.
- Drove the built app through WebKit's WebDriver on a headless X display (`TAURI_WEBVIEW_AUTOMATION=true`,
  `webkitgtk:browserOptions` with the program's path; this is what `tauri-driver` wraps). Scripts were throwaway.

**Worked under WebKitGTK**
- The app starts in about 1 s; the kid picker, home, coloring and driving screens draw as on Windows.
- Coloring: the page opens, a bucket fill lands (the worker, `createImageBitmap`, `OffscreenCanvas`).
- Driving: WebGL 2 starts, the picker and the island load, no page errors.
- Shipped mp3 and wav files decode. The storage files and the maps folder are made in
  `~/.local/share/org.crayonbox.coloring`.

**Broken or missing on Linux**
- **Finished pictures are never written.** The temp file starts with a dot (`.<name>.tmp`, `tauriFiles.ts`), and
  on Linux the fs plugin's scope does not match dot files: "forbidden path". The folders are made, the picture
  is not. Fix: a temp name without the dot, or `requireLiteralLeadingDot: false` for the fs plugin.
- **The Pictures folder needs the account's standard folders** (`~/.config/user-dirs.dirs`). Without them the app
  makes no `Coloring Book` folder and says nothing. Desktop installs have them; a bare kiosk account may not.
- **The build stops inside the compiler**: off Windows the key rules in `kiosk.rs` have no caller, and Ubuntu's
  rustc 1.93.1 crashes while printing those dead-code warnings. `#[cfg_attr(not(windows), allow(dead_code))]` on
  `mod kiosk;` got past it. Not tried with rustup's compiler, which CI uses.
- No `speechSynthesis` at all (the letters fallback voice stays silent), and no WebP encoding from a canvas.

**Not answered by this trial**
- Speed: the headless display draws in software (about 7 frames a second at 1280 × 800), which says nothing
  about a real laptop. WebGL reports "Apple GPU" on every Linux machine, so the app can't tell either.
- The microphone: the test driver grants it by itself. In a normal run nothing answers WebKitGTK's permission
  request (Tauri sets no handler), so recording needs a try by hand.
- Touch, pen, full screen and the close request (no touch device and no window manager on the headless display),
  the autostart entry, the updater, whether sounds are heard, and an AppImage on an older distro (this one was
  built on 26.04; a release build should come from 22.04).

**Next**
- The owner decides whether Linux goes on the to-do list. If so: an ADR, the two fixes above, then the AppImage
  on the real laptop for speed, touch, sound and recording.
